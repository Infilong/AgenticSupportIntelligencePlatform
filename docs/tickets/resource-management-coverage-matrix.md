# Resource Management Coverage Matrix

## Goal
Record the current audit result for user-owned resources, uploaded/imported files, and frontend surfaces that can grow as workspaces accumulate data.

## Audit Rule
If the app lets a user create, import, upload, or accumulate a resource, the app must also provide a management path appropriate to that resource:

- inspect or open details
- edit, reindex, or rerun where relevant
- organize with folders, saved scopes, filters, search, or bounded lists
- delete or archive when the user has permission and when evidence retention allows it
- preserve auditability for AI decisions, costs, traces, reviews, and evaluations
- avoid large flat form controls that accumulate file names, dataset names, document names, run names, or agent names without folders/search/pagination

## Frontend Large-Field Rule
Any frontend field or panel that can grow through user-created resources must use the resource-management pattern instead of an unbounded native dropdown or a long flat list:

- folder scope when the resource is user-owned and library-like;
- searchable picker or searchable list when selection is needed inside a workflow;
- backend `limit` and `offset` when the dataset can grow beyond local demo size;
- clear page/range text so users know which slice is loaded;
- row-level lifecycle controls, such as move, edit, reindex, archive, or delete, when the current role permits them.

Plain native selects are acceptable only for small fixed enums, such as language, status, role, mode, provider type, and label type.

## Current Conclusion
No current file-backed or import-backed resource is upload-only. The app now provides management controls for the resources that users directly create or upload, and it bounds the major non-file operational catalogs that grow from AI runtime activity. File/name-heavy workspace resources are either folder-scoped or loaded through backend-filtered history views instead of accumulating as uncontrolled form fields.

## Intentional Non-delete Decisions
Some records should not be hard-deleted in v1 because they are evidence:

- graph traces
- AI run ledger rows
- tool calls
- guardrail results
- human review decisions
- audit logs
- cost summaries
- evaluation result details

These should remain workspace-scoped, searchable where exposed, and trace-linked rather than being deleted from the UI.

## Remaining Follow-ups
- Add total-count metadata for backend-paginated reviews, tools, guardrails, prompts, models, cost drilldowns, audit logs, and resource libraries before moving beyond local-first/team-scale usage.
- Add resource folders only when a surface becomes a user-created library, not for fixed runtime catalogs or small fixed enums.
- Add import from actual `.jsonl` and document files later if needed; when that happens, the file picker must reuse the same target-folder and post-upload management rules.
- Consider workspace archive/delete only after a clear retention policy exists for traces, ledgers, review decisions, and audit logs.
- Agent model-route assignment now uses a backend-bounded searchable picker instead of a native dropdown over model config history. Apply the same pattern to any future resource-backed form field that can grow beyond a small enum.
- Agent library pagination now uses backend total-count metadata, so folder/search counts and Next-page behavior are not guessed from the current browser page.
